# Technical Specification: Telemetry Pipeline Optimization & Storage Strategy

> [!IMPORTANT]
> **FUTURE IMPLEMENTATION PLAN:** This document serves as a tracking blueprint for addressing long-term telemetry log growth, memory overhead, and disk footprint optimization on the Raspberry Pi kiosk display and Jetson Orin edge server.

---

## 1. Executive Summary & Objective

The objective of this specification is to harden the data engineering pipeline running on the Raspberry Pi kiosk node. It targets the resolution of volatile memory scaling risks (memory leaks) within the asynchronous parsing threads and provides structured options for long-term historical storage.

The core architecture prioritizes maintaining a lean, deterministic resource envelope on the Raspberry Pi kiosk to ensure zero cross-thread performance degradation or micro-stutters.

---

## 2. Current Architectural Data Flow

The kiosk application operates as a multi-threaded telemetry hub on the local network subnet:
* **Ingress Data Path:** Synchronous serial long-polling (`/dev/ttyACM0` at 115200 baud) parsing raw XML string fragments generated by the Rainforest EMU-2 hardware.
* **Secondary Polling Threads:**
  * **SolarEdge Inverter Loop:** Executes a background HTTP GET request every 15 minutes to capture real-time site power flow (PV generation, battery charge/discharge rates, and State of Charge).
  * **Chillicon Matrix Loop:** Executes a background CSRF-authenticated session loop every 10 minutes to extract micro-inverter matrix analytics from the cloud platform.
* **UI & Persistence Layer:** Data points are committed directly to standard flat CSV logs (`*_history.csv`) and passed to memory arrays to draw a rolling 24-hour viewport on a fullscreen Matplotlib canvas wrapped in a Tkinter main window.

## 3. Vulnerability Analysis: In-Memory Scaling Errors

During continuous execution over extended timelines, the application is vulnerable to Out-of-Memory (OOM) kernel panics due to uneven boundary constraints on tracking arrays.

### A. The SolarEdge Battery Tracking Leak (Resolved)
Inside `fetch_solaredge_data()`, an array length check is used to evict data older than the 24-hour window (`self.max_points = 5760` points). 
* *Omission Point (Previously identified):*
  ```python

      self.se_battery_power.pop(0)
      self.se_battery_timestamps.pop(0)
      # self.se_battery_soc.pop(0) <-- OMISSION POINT
  ```
* *Current Status:* **VERIFIED AND RESOLVED.** Line 708 in [dashboard.py](file:///Users/treven/Documents/rainforest-emu2-grid-dashboard/dashboard.py) correctly calls `self.se_battery_soc.pop(0)` along with the power and timestamp pops, mitigating this memory leak.

### B. The Chillicon Catchment Loop Edge Case
The Chillicon pipeline utilizes a relative-time while loop for array eviction based on the delta between the oldest entry and the current system time:
```python
cutoff = now - datetime.timedelta(days=1)
while self.chilicon_timestamps and self.chilicon_timestamps[0] < cutoff:
    self.chilicon_timestamps.pop(0)
    self.chilicon_power.pop(0)
    self.chilicon_energy.pop(0)
```
* *Vulnerability:* If the network drops or the cloud API fails for several days, `fetch_chilicon_data()` never executes. The loop is skipped, preventing the relative-time condition from evaluating. Upon reconnection, a massive block of latent data is appended without purging stale history, causing memory consumption spikes.

## 4. Remediation Matrix & Storage Strategies

Four architectural paths have been evaluated to fulfill the minimum requirement of preserving complete telemetry history without degrading application boot speed.

### Option 1: The Code-Level Structural Patch (Lowest Lift)
* **Mechanism:** Add missing index eviction lines to `fetch_solaredge_data()` and convert the Chillicon loop from a time-delta check to a strict structural cap (`len(self.chilicon_power) > self.max_points`).
* **Memory Footprint:** Completely flatlined. Eliminates runtime accumulation loops.
* **Storage Profile:** Flat CSV files continue to expand indefinitely.
* **Trade-off:** Minimal complexity, but requires manual file truncation down the road if large file sizes slow down startup parsing times during `load_history()`.

### Option 2: Linux OS Primitives (`logrotate` + `tail`)
* **Mechanism:** Retain the flat file storage path, but deploy a native Linux `logrotate` rule with the `copytruncate` flag to automatically compress and archive logs monthly. Modify `load_history()` to use a system `subprocess.run(['tail', '-n', '6000'])` primitive on boot instead of parsing the entire file.
* **Memory Footprint:** Bounded to a fixed 24-hour lookback segment on startup.
* **Storage Profile:** Infinite historical preservation via compressed `.gz` chunks on disk.
* **Trade-off:** Highly resilient, utilizes kernel optimization, and keeps the Python logic exceptionally clean.

### Option 3: Embedded Relational Engine (SQLite)
* **Mechanism:** Strip out file-append commands and integrate an embedded SQLite engine (`telemetry.db`). Add database indexing on timestamps and rewrite `load_history()` to use a precise SQL query:
  ```sql
  SELECT timestamp, demand FROM grid WHERE timestamp >= ?
  ```
* **Memory Footprint:** Highly optimized; leverages indexed lookups to load data instantly.
* **Storage Profile:** Single indexed binary file that safely scales into millions of rows.
* **Trade-off:** Higher upfront refactoring effort, but excellent structural robustness.

### Option 4: Pre-Aggregated Analytics Archive (Recommended)
* **Mechanism:** Enforce strict 24-hour limits on the viewport CSV files so they never grow beyond 5,760 lines. Write a single function that fires once an hour to capture the output of `generate_hourly_summaries()` and append that compact matrix to a permanent analytics file.
* **Memory Footprint:** Consistently low.
* **Storage Profile:** Provides a **99.5% reduction in disk consumption**. Compresses high-frequency 15-second data intervals into optimized hourly rows containing averages, medians, minimums, and peaks.
* **Trade-off:** High structural efficiency that preserves analytical value while minimizing storage wear.

## 5. Downstream Local ML Pipeline Compatibility

The choice of historical storage directly dictates the performance of the downstream machine learning integration on the local Jetson Orin accelerator node.

Feeding millions of raw, 15-second sequential lines across a network link introduces severe token overhead and input latency taxes. Utilizing the **Pre-Aggregated Hourly Summary (Option 4)** reduces an entire year of multi-device telemetry to exactly **8,760 clear, feature-rich rows**. This allows the local edge model to ingest comprehensive annual trends instantly within a single standard context window, ensuring ultra-fast local inference execution times.

## 6. Future Roadmap: Parameterizing Pipeline Loops and Freshness Windows

Currently, the telemetry sync and cache polling loops contain hardcoded time constants:
- **`stage_batch_summary.py`**: Hardcoded to verify a 4-hour cache limit and sleep for 4 hours.
- **`dashboard.py`**: Hardcoded to query the Jetson delta endpoint every 15 minutes and check for local summaries every 10 seconds.

### Proposed Parameterization Strategy
To avoid hardcoding temporal logic and ease system tuning, these values should be moved into the `.env` configuration template:

```ini
# Telemetry Interval & Cache Tuning Parameters
CLOUD_BATCH_INTERVAL_HOURS=4
LOCAL_DELTA_INTERVAL_MINUTES=15
GUI_CACHE_POLL_INTERVAL_SECONDS=10
```

Both `stage_batch_summary.py` and `dashboard.py` will be modified to load these variables with safe defaults (e.g., falling back to `4` hours and `15` minutes if the `.env` variables are missing). This allows operators to scale polling behavior dynamically without editing python codebase paths.
